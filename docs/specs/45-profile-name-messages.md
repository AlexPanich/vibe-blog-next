# 45. Профиль: смена имени и «Кто может мне писать»

| | |
|---|---|
| Статус | done (проверено в браузере); план — `45-profile-name-messages.plan.md` |
| Lifecycle | `user.md` — поля профиля; `message.md` — кто может писать |
| Источник идеи | спека 42, «Не сделано»: поле «Имя» и три варианта в секции «Личные сообщения» |
| Зависит от | 11 (профиль), 21 (личные сообщения), 26 (блокировка), 42 (вид профиля), 50 (выбор собеседника) |

## 1. Цель

В макете профиля (`office/profile`):

- поле «Имя» в секции «Публичная страница». Сейчас имя задаётся при регистрации, а в
  `UserBioForm` показано `readOnly` с подписью «сменить пока нельзя»;
- «Кто может мне писать» — три варианта: «Все», «Мои подписки», «Никто». Сейчас это один
  флаг `messagesFriendsOnly` — «только друзья» (взаимные подписки).

## 2. Решения

**Имя**

1. Своё action `updateNameAction` в `userAccountActions.ts`. better-auth `updateUser` не
   трогаем: остальные поля профиля мы тоже пишем сами.
2. Длина — **2–24 символа, одинаково при регистрации и в профиле**. Сейчас при регистрации
   2–16 (`userSignupDto`). Нормализация до проверки длины: `trim`, повторные пробелы
   схлопываются в один (как у `nameGenitive`). Схема имени — одна на обе dto. Уже
   существующие имена короче 16 символов, поэтому CHECK в БД ничего не ломает.
3. Частота — **не чаще раза в сутки**, по колонке `users.name_changed_at` (а не через
   rate limiter): ограничение переживает перезапуск, и форма может сказать, когда снова
   можно. `null` — имя ещё не меняли, сменить можно сразу. Проверка и запись — одной
   транзакцией. Ошибка — 429 с текстом «Имя можно менять раз в сутки — снова можно
   <дата/время>». Сохранение того же имени (после нормализации) — не смена: ничего не
   пишем и счётчик не трогаем.
4. Журнал не нужен (это не admin-действие), истории имён нет.
5. Имя видно почти везде (шапка, карточки, посты, комментарии, авторы, сообщения), поэтому
   после смены — `revalidatePath('/', 'layout')`. Смена бывает не чаще раза в сутки, так что
   полный сброс дёшев. RSS обновится сам за 10 минут (кэш в памяти). Аватар в шапке и `useUser()`
   в кабинете обновляет `router.refresh()`: пользователь приходит из layout (см. CLAUDE.md, Auth).
6. Уникальность имени не требуется. Защита от выдачи себя за другого — только частота
   смены (п. 3); handle/ник — вне scope.

**Кто может писать**

7. Флаг заменяется enum `users.messages_from`: `all` | `following` | `nobody`. Три
   варианта, как в макете:
   - `all` — «Все»: любой;
   - `following` — «Мои подписки»: те, на кого подписан **я** (получатель);
   - `nobody` — «Никто».
   Варианта «Только друзья» (взаимные) больше нет.
8. Миграция: `messages_friends_only = true` → `following`, иначе `all`. `following` чуть
   шире прежнего «друзья»: писать смогут и те, на кого я подписан без взаимности. Это
   принято: правило проще, и решает его только сам получатель.
9. **Ответ всегда можно.** Настройка получателя не действует, если получатель сам писал в
   этом диалоге: в диалоге есть сообщение, где `userId = recipientId`. Тогда отправка — это
   ответ ему. Сейчас «только друзья» проверяется при каждой отправке, и человек, которому
   я написал, может не суметь мне ответить. Это исправляется.
   - Тот, кто написал до смены настройки и ответа не получил, писать больше не сможет:
     это «новая» переписка, ответа в ней нет.
   - Удалил получатель все свои сообщения — исключение пропадает (вычисляется, не хранится).
   - Бан, блокировка (спека 26) и «Запретить писать» действуют всегда, исключения нет.
10. Staff (`moderator`, `admin`) обходит `messages_from` целиком, включая `nobody`, как
    сейчас обходит «только друзья». Запрет и блокировку staff не обходит.
11. Причины (вместо поля ввода, в выборе собеседника — серой строкой):
    - `following` — «Пользователь принимает сообщения только от тех, на кого подписан»;
    - `nobody` — «Пользователь не принимает новые сообщения».
    Всё по-прежнему в одном `writeBlockReason` (`messageAccess.ts`): отправка, шапка диалога,
    выбор собеседника (спека 50) и страница автора получают правило автоматически.
12. Action `updateMessagesFromAction` вместо `updateMessagesFriendsOnlyAction`
    (`messageSettingsActions.ts`), dto — `z.enum(MESSAGES_FROM)`. Сохраняется сразу по
    выбору, как сейчас.

## 3. Данные

Одна миграция, написанная руками (`ADD COLUMN`, без пересборки `users`, пример —
`0009_post_types.sql`):

```sql
ALTER TABLE `users` ADD `messages_from` text DEFAULT 'all' NOT NULL
  CHECK (`messages_from` IN ('all', 'following', 'nobody'));
UPDATE `users` SET `messages_from` = 'following' WHERE `messages_friends_only` = 1;
ALTER TABLE `users` DROP COLUMN `messages_friends_only`;
ALTER TABLE `users` ADD `name_changed_at` integer;
```

`DROP COLUMN` в SQLite ≥ 3.35 работает без пересборки таблицы, если на колонке нет индекса,
UNIQUE, FK или CHECK. У `messages_friends_only` ничего такого нет, поэтому старую колонку
удаляем сразу, а не «потом». CHECK на длину `name`: `ADD CONSTRAINT` SQLite не умеет, а
пересборка `users` упадёт, поэтому длина проверяется только в zod. Миграцию прогнать на
копии базы через `drizzle-orm` migrator (CLAUDE.md, «База данных») и сверить снапшот
drizzle-kit.

Схема: `MESSAGES_FROM = ['all', 'following', 'nobody'] as const` рядом с `USER_ROLES`,
`messagesFrom: text('messages_from', { enum: MESSAGES_FROM })`, `nameChangedAt` — timestamp.
better-auth обе колонки не знает: в `additionalFields` их не добавлять.

Демо-сид (`scripts/seed-demo/`): если там задаётся `messagesFriendsOnly` — заменить на
`messagesFrom`, оставить хотя бы по одному пользователю с `following` и `nobody`.

## 4. UI

- «Публичная страница» (`UserBioForm`): поле «Имя» становится редактируемым. Своя форма и
  кнопка или общая с «О себе» — решает план. Важно одно: ошибка частоты не должна мешать
  сохранить «О себе», то есть имя уходит отдельным action, и только если изменилось.
  Подпись под полем: «Видно на странице автора, у постов и комментариев. Менять можно раз в
  сутки». После смены — «Снова можно <LocalDate>», пока сутки не прошли.
- «Личные сообщения»: `MessagesFriendsOnlyForm` → `MessagesFromForm`, три радио-карточки
  в ряд (десктоп) или список (телефон) — как в макете «Кабинет — Профиль»; классы
  `ui-account-options` уже есть. Подписи:
  - «Все» — «Любой пользователь»;
  - «Мои подписки» — «Те, на кого вы подписаны»;
  - «Никто» — «Новые переписки закрыты».
  Под карточками: «Ответить вам можно всегда, если вы написали первым. Модераторы и
  администраторы могут написать всегда».

## 5. Lifecycle

- `message.md`, таблица «Кто может писать»: строку «только от друзей» заменить двумя
  (`following`, `nobody`), добавить правило ответа (п. 9) и обход staff (п. 10). Упоминания
  «только от друзей» в разделах выбора собеседника — заменить на «настройка получателя».
- `user.md`: поле `name` (2–24, раз в сутки, `name_changed_at`) и `messages_from`.

## 6. Вне scope

Смена email (уже есть), публичный ник/handle, история имён, уникальность имени.

## 7. Открытых вопросов нет

Обсуждены: три варианта и перенос «друзей» в «Мои подписки» (п. 7–8), ответ всегда
можно (п. 9), раз в сутки по колонке (п. 3), 2–24 везде (п. 2). Остальное (п. 5, 10–12,
удаление старой колонки сразу) принято само, по аналогии.

## 8. Отклонения при реализации

- Текст 429 — «Имя можно менять раз в сутки», без даты (план, решение 3): дату на сервере
  пришлось бы форматировать в его поясе. По 429 форма делает `router.refresh()`, и дату
  показывает подпись под полем через `LocalDate` в поясе браузера.
- Пока срок не прошёл, поле «Имя» показывает имя с сервера, а не введённое: после 429 в
  устаревшей вкладке иначе осталось бы несохранённое имя.
- CHECK на длину `name` нет (§3): длина проверяется только zod; фраза в п. 2 про CHECK устарела.
