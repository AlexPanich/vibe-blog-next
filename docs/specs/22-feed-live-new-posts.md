# 22. Новые посты в ленте без перезагрузки

| | |
|---|---|
| Статус | done |
| Lifecycle | `post.md` — вход в `published`, дата публикации |
| Источник идеи | next-2, спека 38 «Новый пост появляется в ленте сам» |
| Зависит от | 05 (лента), 20 (SSE) |

## 1. Цель

Читатель открыл `/posts`, долистал до середины, а через десять минут вышел новый пост.
Сейчас он об этом не узнает: лента — снимок на момент загрузки. Хотим, чтобы лента сама
предлагала обновиться и при этом не сбивала с места, где человек читает.

## 2. Решения

По аналогии с next-2. П. 5, 6 и 8 обсуждены с человеком, остальные — проверить:

1. **Плашка «Новые посты (N)» с кнопкой «Показать»** над списком, а не вставка карточки и
   не тост. Вставка сверху сдвигает список, и человек теряет место (next-2, 38).
2. **Кнопка перечитывает первую порцию**, а не дописывает пост в начало: дописывание
   сломало бы счётчик «Показано N из M» и смещение догрузки (спека 05), а `?limit=` в URL
   сбрасывается на первую порцию. После показа — прокрутка к началу списка.
3. **Плашка — только в «чистой» ленте:** `/posts` без поиска, типа, рубрик, автора,
   периода и при сортировке «Новые». Во всех остальных режимах новый пост может не
   подойти под условия или оказаться в конце, и плашка обещала бы то, чего нет. Решает
   клиент: сервер не знает, какая страница открыта во вкладке.
4. **Счётчик копит id**: три новых поста — «Новые посты (3)», повтор одного id не
   считается. Пост, ушедший из ленты до нажатия, на кнопку не влияет — первая порция
   просто придёт без него.
5. **«Новые» — по дате первой публикации, а не создания.** Сейчас сортировка идёт по
   `createdAt`, то есть по дате черновика: пост, который писали неделю, после одобрения
   встаёт глубоко в ленту, и «Показать» его не покажет. Ключ сортировки — `announcedAt`
   (спека 20: ставится при первом `approve`, у старых постов заполнен миграцией),
   переименованный в `publishedAt`. Дата в карточке и на странице поста — тоже она; у
   поста, который ещё не публиковался (автор смотрит черновик), — `createdAt`.
6. **Событие — только при первой публикации**, как уведомление `post.published`
   (спека 20, п. 5). `restore` и `unblock` дату публикации не меняют, пост возвращается на
   своё место в ленте, а не наверх, — плашке нечего показать.
7. **Автору поста и модератору, который одобрил, событие не шлётся** — они и так знают.
8. **Гости получают событие.** Это самая частая аудитория ленты. `/api/events` открыт без
   сессии: гость подписан только на широковещательные события, адресные ему не приходят.
9. **Поток гостя открывается, только пока на странице есть подписчик широковещательного
   события** — то есть на «чистой» ленте. Иначе каждая открытая вкладка гостя на любой
   странице держала бы соединение. У вошедшего поток открыт всегда, как сейчас.
10. **Лимит потоков гостя — 5 на IP**, шестой закрывает самый старый (как
    `STREAMS_PER_USER`). Переподключения держит глобальный лимит `proxy.ts`. Без прокси
    перед приложением все гости — один IP (CLAUDE.md, «IP и env»), лимит придётся
    поднять или настроить `TRUSTED_PROXY_HOPS`.

## 3. Данные и транспорт

- Миграция: `posts.announced_at` → `published_at` (`RENAME COLUMN`, без пересборки
  таблицы), индекс `(status, published_at)` для ленты. Тай-брейкер в сортировках «Рейтинг»
  и «Автор» — тоже `publishedAt`.
- `liveBus`: рядом с подписчиками по `userId` — гостевые по IP;
  `broadcast(type, data, exceptUserIds)` шлёт всем (вошедшим и гостям). Адресный
  `publish` гостей не трогает.
- Типы событий делятся на адресные и широковещательные: гостю — только вторые
  (`LIVE_BROADCAST_EVENT_TYPES` в `shared/liveEvents.ts`).
- Событие `post.published` в `LiveEvents`: `{ postId }`. Только сигнал «перечитай» —
  без заголовка и автора, иначе появился бы второй формат карточки, который разойдётся с
  `loadFeed` (next-2, 38 §3.1).
- Отправка — в `changePostStatus` после commit, когда переход поставил `publishedAt`
  (первый `approve`).

## 4. UI

- `FeedList` в «чистом» режиме подписывается на `post.published`; плашка — над списком,
  липкая под шапкой, «Новые посты (3) · Показать».
- `LiveEventsProvider`: у гостя `EventSource` открывается при первом подписчике
  широковещательного события и закрывается, когда подписчиков не осталось. Вход и выход
  переоткрывают поток.
- `office/feed` (лента подписок) — без плашки (п. 3).

## 5. Вне scope

Вставка карточки без кнопки, превью нового поста в плашке, плашка на странице автора и в
ленте подписок, живое обновление счётчиков оценок и комментариев в карточках, подъём
поста наверх при восстановлении из архива.

## 6. Открытые вопросы

- **Несколько инстансов.** Широковещание, как и адресная шина, живёт в одном процессе.

## 7. Что показала проверка

Прогон в браузере (гость, alice — admin, bob — автор, some — moderator; пост bob на
модерации с датой создания старше всех опубликованных): гость на `/posts?sort=old` и
`/posts?type=travel` потока не открывает, на `/posts` — один; после одобрения плашка
«Новые посты (1)» у гостя и alice, у bob и some — нет; «Показать» — пост первым с
сегодняшней датой, «Показано 6 из 6», `?limit` сброшен, прокрутка к списку; архив и
восстановление поста bob события не дают — всё сходится.

- **Колокольчик у гостя.** `NotificationBell` смонтирован и у гостя (разметку не выводит), а
  его обработчик `open` перечитывал счётчик — с гостевым потоком это стало `401` на
  каждое подключение. Перечитывание теперь только при пользователе; это закрыло и
  `visibilitychange`, который делал то же самое и раньше.
- **Пустая лента.** При `total === 0` страница вместо `FeedList` показывает «Ничего не
  нашлось», плашки там нет. Для «чистой» ленты это возможно, только пока на сайте нет ни
  одного поста, — оставлено.
- **Снапшот миграции** собран из 0016 (`jq`), SQL написан руками: drizzle-kit спрашивает про
  переименование интерактивно. Проверено `drizzle-kit generate` — «No schema changes».
- Не проверены вручную: шестая вкладка гостя закрывает старейший поток (та же функция, что
  у вошедших) и лимит потоков при общем IP без прокси.
