# 07. Оценки постов

| | |
|---|---|
| Статус | done |
| Lifecycle | `docs/lifecycles/post.md` — оценки опубликованного поста |
| Источник идеи | next-2, спеки 19 «Рейтинг постов» и 42 (средняя автора) |

Решения приняты без обсуждения (человек попросил работать без остановки), подтверждены на проверке 2026-10-27.

## 1. Цель

Читатель оценивает пост звёздами 1–5, все видят среднюю и число оценок. Лента
сортируется по рейтингу, страница авторов показывает и сортирует по средней автора.

## 2. Решения

1. **Оценивает вошедший, только `published`, не свой пост.** Автор не голосует за себя —
   иначе своя же рука смещала бы его среднюю. Гость видит «Войдите, чтобы оценить».
   Забаненному отдельного правила не нужно: войти он не может (спека 02).
2. **Одна оценка на пару пост–пользователь**, повторная перезаписывает. «Снять оценку» —
   отдельная ссылка под звёздами.
3. **Средняя до десятых через запятую и счётчик**: «4,2 · 3 оценки». Нет оценок — «Нет
   оценок», а не «0,0».
4. **Своя оценка грузится на клиенте после гидрации** (`myPostRatingAction`): публичная
   часть сессию на сервере не читает (`ClientSideInitializer`, спека 01). Сервер отдаёт
   среднюю и счётчик.
5. **Карточка в ленте — только чтение**, строка рейтинга есть, только если оценки есть.
6. **Оценки переживают уход поста из ленты** (архив, блокировка, снятие с публикации) и
   возвращаются вместе с ним. Отдельного сброса нет: у поста одна версия.
7. **Средняя автора — взвешенная** (сумма оценок / число оценок) по **опубликованным**
   постам: пост с двумя оценками не весит как пост с двадцатью, а скрытого поста нет и
   в ленте. Автор без оценок — карточка без строки рейтинга.
8. **Сортировка «по рейтингу»** в ленте: средняя по убыванию, при равной — больше оценок,
   затем свежие. Посты без оценок — в конце, а не как ноль. То же на странице авторов.
9. **Оценка проверяет статус в той же транзакции**: пост ушёл из ленты, пока читатель
   жал звезду, — «Пост больше не опубликован», а не тихая запись.

## 3. Данные

`post_ratings`: `postId`, `userId`, `value` (CHECK 1–5), `createdAt`, `updatedAt`, PK
`(postId, userId)`, индекс по `postId` входит в PK. Агрегаты не храним — считаем
запросом (`avg`, `count`).

## 4. UI

- Страница поста: блок «Оценка» после текста, перед комментариями: Mantine `Rating`,
  подпись, «Снять оценку». Своё — заливкой.
- Карточка: «★ 4,2 (3)» в мета-строке.
- Лента: сортировка «По рейтингу».
- Авторы: «★ 4,2» в карточке, сортировка «По рейтингу».

## 5. Вне scope

Оценки в кабинете и модерации, список «кто оценил», антифрод, уведомления об оценках.

## 6. План и реализация

- `post_ratings` + миграция `0005`; `posts/shared/postRatings.ts` — агрегаты одним запросом
  на список, подзапрос для сортировки ленты; `posts/actions/postRatingActions.ts` —
  `ratePostAction` (upsert/delete в транзакции со статусом) и `myPostRatingAction`.
- `PostRatingBlock` (client, Mantine `Rating`) на странице поста, `PostRatingBadge` в
  карточке, `rating` в `postResource`.
- Лента: сортировка `rating` — left join агрегата, `IS NULL` в конец. Авторы:
  `avg(post_ratings.value)` по join опубликованных постов — это и есть взвешенная средняя;
  посты считаются `countDistinct`, иначе join с оценками размножил бы их.

## 7. Что показала проверка

- **Бесконечный цикл запросов своей оценки.** `execute` из `useAction` меняется на каждом
  рендере и стоял в зависимостях эффекта: запрос → рендер → запрос, пока глобальный лимит
  proxy не начал отвечать 429. Защита — метка «уже загружено для этого пользователя» в
  `useRef`. Касается любого эффекта, который вызывает `execute`.
