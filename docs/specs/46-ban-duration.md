# 46. Срок блокировки пользователя

| | |
|---|---|
| Статус | реализовано (`46-ban-duration.plan.md`), следующая фаза — проверка |
| Lifecycle | `user.md` — «Заблокирован», «Журнал», уведомления |
| Источник идеи | спека 42, «Не сделано»: выбор «7 дней / 30 дней / Навсегда» в карточке «Блокировка» |
| Зависит от | 02 (бан), 26 (блокировка), 42 (вид карточки пользователя) |

## 1. Цель

Сейчас бан бессрочный: `users.bannedAt` + `banReason`, снимает только admin. В макете
«Админ — Пользователь» у блокировки есть срок.

## 2. Решения

1. **Варианты срока:** 7 дней, 30 дней, навсегда. По умолчанию выбрано **7 дней**.
   Срок — точный момент: `now + 7 × 24 ч` (не «до конца дня»).
2. **Данные:** новое поле `users.banned_until` (NULL — навсегда). Срок пишется в журнал
   отдельной колонкой `user_admin_actions.until`, а не в `comment`: там причина. Колонка
   заполняется только у `banned` (у навсегда — NULL).
3. **Бан вычисляется, а не снимается.** Бан действует, если `bannedAt` есть и
   `bannedUntil` равен NULL или в будущем. Задачи очереди нет, «системного» actor тоже,
   так что `actor_id NOT NULL` остаётся как есть.
   - Одно условие — хелпер: SQL-фрагмент для запросов и JS-функция для загруженной
     строки. Он заменяет голую проверку `bannedAt` **во всех местах**: хук входа
     (`globals/auth.ts`), фильтр и счётчик «Заблокированные» (`loadAdminUsers`), пилюля
     в списке и в hero, карточка на странице пользователя, `messageAccess` и
     `loadMessagePicker`, рассылки staff/admin в `notify.ts`, проверка исполнителя и цели
     в `userAdminTransaction` / `userAdminActions`, `loadAdminAuthorRequests`.
   - Когда истёкший бан встречается при входе, хук лениво обнуляет `bannedAt` /
     `banReason` / `bannedUntil` и пропускает вход. Это уборка, а не событие: записи в
     журнал и уведомления нет. Пока человек не вошёл, поля остаются, но хелпер
     показывает, что бан истёк.
   - В журнале остаётся «Заблокирован до 16 ноября»: срок виден из самой записи.
     Отдельной строки «разблокирован по сроку» нет.
4. **Уведомление `user.unbanned`** уходит только при ручном разбане, как сейчас. При
   истечении срока его нет: человек просто снова может войти.
5. **Форма входа:** «Аккаунт заблокирован до 16 ноября: <причина>», у навсегда —
   «Аккаунт заблокирован: <причина>», как сейчас. Дату форматирует клиент (часовой пояс
   браузера, скил `hydration`). Сервер отдаёт срок вместе с кодом 423, а не готовой
   строкой.
6. **Сменить срок у действующего бана нельзя:** разблокировать и заблокировать заново.
   Журнал остаётся линейным, нового действия в `USER_ADMIN_ACTIONS` нет.
7. **Существующие баны** после миграции — навсегда (`banned_until` NULL). Демо-сид
   заблокированных не создаёт и не меняется.
8. Сессии отзываются в момент бана, как сейчас, при любом сроке.

## 3. Данные

Миграция руками через `ADD COLUMN`: на `users` ссылаются другие таблицы, пересборка
упадёт (см. `CLAUDE.md`, «База данных»).

- `users.banned_until` — `integer` timestamp, nullable.
- `user_admin_actions.until` — `integer` timestamp, nullable. CHECK на колонке: `until`
  только у `banned` (`until IS NULL OR action = 'banned'`). Если CHECK со ссылкой на
  другую колонку в `ADD COLUMN` не пройдёт, проверку оставить в zod/action и записать
  это отклонение сюда.

## 4. UI

- Карточка «Блокировка» в «Админ — Пользователь»: причина, три пилюли срока
  (7 дней выбрано), кнопка «Заблокировать».
- Карточка заблокированного: «Заблокирован <дата> · до 16 ноября» или «· навсегда»,
  причина, «Разблокировать».
- Список пользователей: у заблокированного рядом с пилюлей — «до 16 нояб» или
  «навсегда». Пользователь с истёкшим сроком выглядит обычным.
- Журнал: «Заблокирован до 16 ноября: <причина>» / «Заблокирован навсегда: <причина>».
- Все даты — `LocalDate`.

## 5. Lifecycle

`user.md` правится вместе с реализацией:

- «Заблокирован»: вместо «Бан бессрочный» — сроки, вычисляемое истечение, ленивая уборка
  при входе, нельзя сменить срок;
- «Журнал»: срок в записи бана, строки об истечении нет;
- уведомления: `user.unbanned` — только при ручном разбане.

## 6. Вне scope

Частичные ограничения (только комментарии, только посты), бан по IP, произвольный срок,
смена срока действующего бана, письмо о бане и о его окончании.

## 7. Реализация

Отклонений от плана нет.

- CHECK на `user_admin_actions.until` работает в `ADD COLUMN` (миграция `0028` написана руками). В
  `schema.ts` он объявлен на уровне таблицы, чтобы был в снапшоте drizzle-kit.
- Срок до формы входа доходит в теле `APIError` из хука (`e.body.until`). Запасной путь с чтением
  `users` в `throwSigninError` не понадобился.
