# Resource: данные на границе сервер → клиент

Всё, что серверный компонент передаёт клиентскому, сериализуется и попадает в браузер. Поэтому каждое такое значение должно быть сужено до явно описанной схемы и проверено zod. Для этого есть готовые инструменты:

- `resource(schema, value)` — вызывается на сервере, возвращает проверенное значение, которое можно передать в клиентский компонент;
- `StrictResource<T, U>` — тип пропса клиентского компонента, который принимает только результат `resource()` и не допускает лишних полей.

По умолчанию они импортируются из `@/core/resource`. Если в проекте такого модуля нет, спроси у человека, где лежат эти утилиты, и обнови путь в этом скиле.

## Правила

### 1. Сервер → клиент — всегда через `resource()`

Без исключений. Через `resource()` идут объекты, массивы и примитивы, включая одиночный `id`, строку и число.

```tsx
// серверный компонент
<PostView post={resource(postResource, post)} />
<RemoveButton id={resource(idResource, post.id)} />
```

```tsx
// неправильно: сырая строка из БД уходит в браузер целиком
<PostView post={post} />
```

### 2. Отдельная валидация не нужна

Проверка zod-схемой встроена в `resource()`. Правила 1 достаточно, чтобы ничего не ушло в клиент непроверенным.

### 3. Где лежат схемы ресурсов

Схемы ресурсов лежат в домене, которому принадлежит сущность. По умолчанию это `src/domains/<domain>/dto/<entity>Resources.ts`.

**Если такой папки в проекте нет**, спроси у человека, где в его структуре лежат ресурсы, и **обнови путь в этом скиле** на указанный.

Схема, которая нужна другому домену, отдаётся через его `exports/`, а не импортируется из чужого `dto/` напрямую.

Пока домен простой, все его ресурсы в одном файле. Когда файл разрастается, он делится по разделу или назначению, раздел входит в имя, папка остаётся плоской:

```
domains/<domain>/dto/
  <entity>PublicResources.ts
  <entity>AdminResources.ts
```

### 4. Именование

- Схема: `camelCase` с суффиксом `Resource` (`postResource`, `authorResource`, `postListResource`).
- Тип: `PascalCase` с тем же именем, выводится только через `z.infer`.
- Схема и её тип лежат в одном файле.

```ts
export const postResource = z.object({
  id: z.number(),
  title: z.string(),
  author: authorResource,
})

export type PostResource = z.infer<typeof postResource>

export const postListResource = z.array(postResource)

export type PostListResource = z.infer<typeof postListResource>
```

### 5. Вложенные ресурсы

Ресурс одной сущности можно вложить в ресурс другой: схема автора лежит в домене пользователей, ресурс поста её импортирует. Схемы не дублируем, но граница доменов соблюдается: домен-владелец отдаёт схему через свой `exports/`, а чужой домен импортирует её только оттуда (`@/domains/<domain>/exports/…`), не из `dto/` напрямую.

### 6. Пропсы клиентского компонента, получающего данные от сервера

Такие пропсы всегда типизируются через `StrictResource`, без исключений. Обычный тип ресурса пропустил бы объект с лишними полями. `Resource` в инструментарии есть, но в пропсах его не используем.

```tsx
'use client'

type Props<T extends PostResource> = {
  post: StrictResource<T, PostResource>
}

export default function PostView<T extends PostResource>({ post }: Props<T>) {
  …
}
```

### 7. Клиент → клиент — без `resource`

Если клиентский компонент передаёт данные другому клиентскому, `resource()` и `StrictResource` не нужны: данные уже в браузере, граница пройдена. Пропсы типизируются обычным типом ресурса или его частью.

```tsx
'use client'

export default function PostCard({ post }: { post: PostResource }) { … }
```

### 8. Сервер рендерит клиентский компонент, написанный для передачи клиент → клиент

Решение зависит от того, кто ещё использует этот компонент:

- **его используют другие клиентские компоненты** — только мост: тонкий клиентский компонент со `StrictResource` в пропсах, который прокидывает данные в исходный. Исходный компонент не трогаем.

  ```tsx
  'use client'

  type Props<T extends PostResource> = {
    post: StrictResource<T, PostResource>
  }

  export default function PostCardBridge<T extends PostResource>({ post }: Props<T>) {
    return <PostCard post={post} />
  }
  ```

- **больше никто не использует** — обычно лаконичнее перевести сам компонент на `StrictResource` (правило 6), без моста.

### 9. Сменился тип компонента — перепроверь границы

Компонент, который вчера был серверным, сегодня может стать клиентским, и наоборот. Каждый раз, когда это происходит, правила выше нужно применить заново.

Тип компонента меняется, когда:

- в файл добавили или из него убрали `'use client'`;
- компонент без директивы начали импортировать из клиентского компонента. Тогда он неявно становится клиентским;
- компонент перенесли в другое место дерева или разбили на серверную и клиентскую части.

Что проверить:

- **Компонент стал клиентским.** Найди всех серверных родителей, которые его рендерят: каждый передаваемый проп должен идти через `resource()` (правило 1), а пропсы компонента — быть типизированы через `StrictResource` (правило 6). Если компонент также получает данные от клиентских родителей, используй правило 8.
- **Компонент стал серверным.** Его пропсы больше не пересекают границу. Проверь, где теперь проходит граница: дочерние клиентские компоненты, которым он передаёт данные, должны получать их через `resource()` и `StrictResource`.
- **Компонент разбили на серверную и клиентскую части.** Новая граница проходит между этими частями, и к ней применяются правила 1 и 6.

Не считай, что раз код компилировался до изменения, с ним всё в порядке. Без `StrictResource` в пропсах TS не заметит, что новый серверный родитель передаёт сырые данные.
