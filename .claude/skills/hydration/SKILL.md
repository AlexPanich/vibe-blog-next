# Гидратация: сервер и первый рендер в браузере должны совпадать

Сервер рендерит HTML, ничего не зная о браузере: ни размера окна, ни системной темы, ни сохранённых настроек, ни часового пояса, ни локали, ни того, вошёл ли пользователь. Браузер при гидрации рендерит клиентские компоненты ещё раз, и результат обязан совпасть с серверным HTML. Если не совпал, React выдаёт ошибку и перерисовывает дерево на клиенте.

Как это выглядит:

- `Hydration failed because the server rendered text didn't match the client` — основная ошибка, в ней виден diff `+` / `-`;
- `Encountered a script tag while rendering React component` — часто не самостоятельная ошибка, а следствие первой: после неудачной гидрации React рендерит дерево на клиенте и натыкается на инлайн-скрипт (например, скрипт темы в `<head>`). Сначала ищи и чини несовпадение.

Многие ошибки не видны локально: dev-сервер и браузер на одной машине, у них общие пояс и локаль. См. правило 5.

## Инструменты

- `useHydrated()` — `false` на сервере и во время гидрации текущего компонента, `true` после;
- `useUser()` → `{ user, ready }` — текущий пользователь; `ready` — пользователь известен и компонент уже гидрирован;
- `<UserGate fallback guest auth />` — разметка, зависящая от пользователя;
- `<ClientValue server client />` — значение, которое на сервере и в браузере считается по-разному;
- `<LocalDate value options />` — дата и время в локали и поясе браузера.

По умолчанию хуки лежат в `@/hooks/<имя>`, компоненты — в `@/components/general/<имя>`, всё с default-экспортом. Если в проекте их нет или они лежат в другом месте, спроси у человека и обнови пути в этом скиле.

## Правила

### 1. Как выглядит элемент, решает CSS, а не JSX

Если класс, стиль или CSS-in-JS выбирается условием в JSX по данным клиента, серверная и клиентская разметка расходятся. Поэтому у элемента всегда одни и те же классы, а различия задаются внутри них:

- медиа-запросами: ширина экрана, системная тема, `prefers-reduced-motion` и т. п.;
- селекторами по атрибутам, которые выставлены **до гидрации**. Например, тема из сохранённых настроек, которую инлайн-скрипт в `<head>` ставит на `<html>`.

```tsx
// неправильно
<div className={isMobile ? 'list-compact' : 'list-wide'}>

// правильно: @media внутри .list
<div className="list">
```

Если варианты различаются содержимым, а не только стилем, рендерим оба и прячем лишний через CSS:

```tsx
// неправильно: иконка зависит от темы, которую сервер не знает
{ dark ? <SunIcon /> : <MoonIcon /> }

// правильно: обе иконки в разметке, видимость по атрибуту темы на <html>
<SunIcon className="only-dark" />
<MoonIcon className="only-light" />
```

У UI-фреймворков для этого обычно есть готовые пропсы или классы (`lightHidden` / `darkHidden`, `hiddenFrom` / `visibleFrom` и т. п.). Пользуйся ими.

### 2. Правило 1 применять с умом

Если в UI-фреймворке есть готовый сложный компонент, который подходит по задаче и по духу дизайн-системы, берём его, даже если внутри он выбирает разметку условием, а не через CSS. Велосипеды вместо фреймворка не пишем.

Несовпадение тогда убираем тем, что сервер заранее угадывает данные клиента (размер экрана, тип устройства и т. п.) и рендерит тот же вариант, что получится в браузере.

Угадываем **только через общие хелперы ядра** — единую точку, где на сервере вычисляются данные клиента. В компонентах и страницах `User-Agent`, заголовки и куки руками не разбираем. Хелпер должен давать на сервере и в браузере одинаковый ответ, иначе гидрация снова разойдётся.

Если таких хелперов в проекте нет, не пиши разбор заголовков на месте: скажи человеку, что их нужно завести, и предложи сделать.

### 3. Пользователь в разметке — только через `UserGate` или `useUser()`

Пользователь становится известен в браузере, и сервер не может знать, что увидит клиент в момент гидрации. Поэтому до гидрации разметка от пользователя не зависит.

```tsx
<UserGate
  fallback={<Skeleton />}
  guest={<Link href="/login">Войти</Link>}
  auth={user => <Link href="/profile">{ user.name }</Link>}
/>
```

- При гидрации всегда выводится `fallback`, после неё `guest` или `auth(user)`.
- Все пропсы необязательные: не передан — ничего не выводится.
- `auth` — функция, а серверный компонент не может передать функцию в клиентский. Поэтому `UserGate` с `auth` используется только внутри клиентских компонентов. Из серверного рендери клиентский компонент, в котором стоит `UserGate`.

`useUser()` нужен, когда пользователь нужен в логике, а не в разметке. Пока `ready === false`, веди себя так, будто пользователя ещё нет.

Контекст пользователя напрямую (`useContext`) не читаем.

Глобальный флаг «приложение гидрировано» не заводим. Части страницы под `<Suspense>` гидрируются позже корня, и флаг, поставленный в эффекте корня, для них уже будет `true`, а серверный HTML — нет. Гидрация — свойство конкретного компонента, это и делает `useHydrated()`.

### 4. Дата и время — только через `LocalDate`, остальные клиентозависимые значения — через `ClientValue`

`toLocaleString()`, `toLocaleDateString()` и `Intl.DateTimeFormat` без явных `locale` и `timeZone` берут их из среды выполнения, а у сервера и браузера среды разные. То же с `Date.now()`, `new Date()` и относительным временем («5 минут назад») в рендере: между серверным рендером и гидрацией проходит время.

```tsx
// неправильно
<div>{ post.createdAt.toLocaleString() }</div>

// правильно
<LocalDate value={post.createdAt} />
<LocalDate value={user.createdAt} options={{ dateStyle: 'medium' }} />
```

`LocalDate` при гидрации выводит дату в ISO и UTC, после неё — в локали и поясе браузера. `options` — обычные `Intl.DateTimeFormatOptions`, по умолчанию дата и время. `value` — `Date`. Компонент можно рендерить и из серверных компонентов: дата в серверном компоненте без него показывается в поясе сервера, а не пользователя.

Для других значений, которые по-разному считаются на сервере и в браузере, используем `ClientValue`. Это аналог `data-allow-mismatch` из Vue: гидрация идёт по `server`, после неё побеждает `client`.

```tsx
<ClientValue
  server="—"
  client={() => formatRelative(comment.createdAt)}
/>
```

`server` обязан быть детерминированным, то есть одинаковым на сервере и в браузере. `client` — функция, поэтому ограничение то же, что у `auth` в правиле 3: только внутри клиентских компонентов.

Цена подхода: текст на мгновение меняется после загрузки. Это осознанный выбор.

`suppressHydrationWarning` для этого **не годится**. Он только убирает ошибку: React оставляет в DOM серверный текст и не заменяет его клиентским ни при гидрации, ни при следующих рендерах, пока значение не изменится. Пользователь так и увидит серверный вариант. Допустим только там, где расхождение заранее выставлено в DOM до гидрации (инлайн-скрипт темы на `<html>` и т. п.).

### 5. Проверяй с чужими поясом и локалью

Локально сервер и браузер обычно в одном поясе и одной локали, поэтому ошибки из правила 4 не проявляются, а в проде (сервер почти всегда в UTC) проявляются. Проверяй хотя бы одно из двух:

- запускай dev-сервер с другими поясом и локалью: `TZ=UTC LANG=ja_JP.UTF-8 next dev`. На Windows переменные так не задаются, нужен `cross-env` или отдельный npm-скрипт;
- в браузерном прогоне подменяй пояс и локаль браузера, например в Playwright `newContext({ timezoneId: 'America/Los_Angeles', locale: 'ja-JP' })`, в Chrome DevTools через Sensors.

Проверяй ещё с сохранённой тёмной темой, если тема хранится в `localStorage`, и под гостем и вошедшим пользователем.
